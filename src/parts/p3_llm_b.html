4.6 Kernel 与 runtime：把每一步做快

解决 P8、P9。批处理和调度决定“算什么”，kernel 和 runtime 决定“算得多快”。理解 kernel 最好的办法是沿着一层 decoder 的执行顺序，看每一步调用了哪个 kernel、它是 compute-bound 还是 memory-bound、和谁可以融合。

面试常问的 kernel 概念

概念一句话解释为什么推理里重要
Tiling / 分块把大矩阵切成能放进 shared memory / 寄存器的块，块内复用数据决定算术强度；FlashAttention、GEMM 的核心
Online softmax流式维护 running max 和 running sum，分块算 softmax 而不需要整行attention 不物化 N×N 的前提；split-KV 归约也靠它（合并 LSE）
Warp specialization同一 block 内不同 warp 分工（搬数据 / 计算 / 写回），用 barrier 流水Hopper 之后高性能 kernel 的标准写法（FA3、DeepGEMM）
TMA / WGMMA / tcgen05Hopper 的张量内存加速器做异步块搬运，WGMMA 是 warpgroup 级 MMA；Blackwell 的 tcgen05 MMA 把累加器放到专用的 Tensor Memory（TMEM）不同代际 kernel 无法直接复用，这就是为什么每代 GPU 都有新版 FA / GEMM
Persistent kernel / stream-K / split-K常驻 kernel 循环领取 tile；沿 K 维切分以增加并行度decode 的瘦 GEMM tile 太少，不切就吃不满 SM
Epilogue 融合GEMM 写回前顺便做 bias、激活、量化、残差省掉一次 HBM 往返
Occupancy 与寄存器压力每个 SM 同时驻留的 warp 数受寄存器 / shared memory 限制memory-bound kernel 需要足够多的在途访存来掩盖延迟
PDL / CUDA graphProgrammatic Dependent Launch 让下一个 kernel 提前启动 prologue；graph 一次提交整串 kerneldecode 一步只有几毫秒，launch 间隙占比显著

写 kernel 的工具链：CUDA C++ + CUTLASS / CuTe 仍是性能天花板；Triton 是最常用的 Python DSL（vLLM / SGLang 大量 MoE、attention 变体用它）；CuTe DSL（Python 版 CUTLASS，FA4 用它）、TileLang（DeepSeek 的稀疏 attention 等用它写参考实现）、ThunderKittens 让写 Hopper / Blackwell 专用 kernel 更容易。

4.7 量化：少读字节、多放 KV

源码{{s:vllm-project/vllm:vllm/model_executor/layers/quantization/fp8.py|vLLM fp8.py}}{{s:vllm-project/vllm:vllm/model_executor/layers/quantization|quantization/ 各方法}}{{r:vllm-project/llm-compressor|llm-compressor}}{{r:IST-DASLab/marlin|Marlin}}

解决 P3、P6、P7。decode 是 memory-bound，权重字节数减半，单步时间就接近减半；同时省下的显存给 KV，批更大。prefill 是 compute-bound，只有激活也量化（W8A8、FP8、FP4）且用对应的 Tensor Core 指令时才加速。

方案量化对象收益代表方法 / 硬件注意
Weight-only INT4 / INT8只量化权重，计算时反量化decode 加速明显、显存省 2–4×GPTQ（二阶误差补偿）、AWQ（按激活幅度保护重要通道）；Marlin kernel大批 / prefill 收益小，反量化有开销
W8A8 INT8权重 + 激活prefill 也加速SmoothQuant（把激活离群值“平移”到权重）激活离群值是难点
FP8（E4M3）权重 + 激活，per-tensor / per-channel / 分块 scale近乎无损，算力 2×Hopper 起原生；DeepSeek-V3 用 128×128 分块 scale当前生产最常用
FP4（NVFP4 / MXFP4）权重（+ 激活）再翻倍NVFP4：16 元素一组、FP8 scale（Blackwell）；MXFP4：32 元素一组、E8M0 scale（OCP 标准，gpt-oss 原生发布）更依赖 QAT / 好的校准
KV cache 量化K / VKV 容量 2×、attention 带宽减半FP8 KV 最常见，也有 INT4 KV长上下文任务要专门评测

工具：vLLM 的 llm-compressor、NVIDIA ModelOpt、Intel AutoRound、PyTorch torchao、bitsandbytes、llama.cpp 的 GGUF k-quants。面试常问“量化后怎么验证”：除了 perplexity，一定要在目标任务（数学、代码、长上下文检索）上评测，量化对推理链长的任务更敏感。

4.9 并行策略：模型放不下、或一张卡太慢

源码{{s:vllm-project/vllm:vllm/distributed/parallel_state.py|vLLM parallel_state.py}}{{s:vllm-project/vllm:vllm/distributed/device_communicators/all2all.py|all2all.py}}{{s:sgl-project/sglang:python/sglang/srt/managers/data_parallel_controller.py|SGLang DP controller}}{{s:NVIDIA/Megatron-LM:megatron/core/tensor_parallel|Megatron tensor_parallel}}

解决 P7、P10。推理里的并行与训练相似，但目标不同：训练追求吞吐，推理还要压单请求延迟，所以 PP 在推理中没那么受欢迎（它不降低单 token 延迟）。

并行通信优点缺点推理中的典型用法
TP每层 2 次 all-reduce，量 ∝ batch_tokens × hidden降低单 token 延迟，权重和 KV 都被切分通信频繁，跨机代价大；TP 太大时 GEMM 变瘦机内 TP=2/4/8
PP相邻 stage 点对点传激活通信少，可跨机不降单 token 延迟；需要多个微批才能填满流水超大模型跨机；吞吐优先
DP无（路由层面分流）线性扩吞吐，最简单每个副本都要装下整个模型多副本 + 负载均衡；MoE 的 attention 部分做 DP
EP每个 MoE 层两次 all-to-all（dispatch / combine）专家显存被分摊，每卡专家少 → 每专家批更大负载不均、all-to-all 延迟DeepSeek / Qwen MoE 的大规模部署
CP / SPring 传 KV 或 all-to-all 换 head超长 prompt 的 prefill 可以多卡并行decode 收益小百万 token 级 prefill

4.10 结构化输出、多 LoRA、API 层功能

源码{{s:mlc-ai/xgrammar:cpp|XGrammar cpp/}}{{s:vllm-project/vllm:vllm/v1/structured_output/backend_xgrammar.py|vLLM xgrammar backend}}{{s:sgl-project/sglang:python/sglang/srt/constrained/xgrammar_backend.py|SGLang xgrammar backend}}{{s:vllm-project/vllm:vllm/tool_parsers|vLLM tool_parsers/}}{{s:sgl-project/sglang:python/sglang/srt/function_call|SGLang function_call/}}{{s:vllm-project/vllm:vllm/lora/punica_wrapper|vLLM punica_wrapper}}{{s:sgl-project/sglang:python/sglang/srt/lora/lora_manager.py|SGLang lora_manager.py}}

解决 P11、P12。这些不提升“裸性能”，但是产品必需品，而且做不好会严重拖慢吞吐。

  • 结构化输出（constrained decoding）。把 JSON schema / 正则 / CFG 编译成自动机，每步生成一个 token mask，把非法 token 的 logit 置为 −∞。难点是 mask 计算要在 GPU 前向期间完成、不成为瓶颈。XGrammar 用下推自动机 + 预计算“与上下文无关”的 token 集合，把大部分检查挪到预处理；llguidance、Outlines 是其他实现；SGLang 早期的 compressed FSM 可以一次“跳过”确定的多个 token（jump-forward）。
  • 工具调用与推理内容解析。不同模型的 tool call 格式各异，服务端需要 tool-call parser 和 reasoning parser 把输出转成 OpenAI 格式的 tool_calls 和 reasoning_content。
  • Multi-LoRA。一个基座 + 成百上千个 LoRA adapter 同时服务。S-LoRA 把 adapter 权重与 KV 统一分页管理并按需从 CPU 载入；Punica 的 SGMV kernel 让一个批里不同请求用不同 adapter 仍然高效。vLLM / SGLang 都支持动态加载与批内混合 adapter。
  • 多租户隔离。优先级、配额、按租户的公平调度、按 token 计费与限流（TPM / RPM）。
  • OpenAI 兼容 API。/v1/chat/completions、/v1/completions、/v1/embeddings、/v1/audio/*、Responses API；logprobs、n 采样、stop、seed 等参数都要在引擎里正确实现。
