01推理服务本身：要求与指标

Inference serving 的任务是把训练好的模型变成一个服务：接收请求、在加速器上跑前向、把结果（常常是流式地）返回。它要同时满足三类目标，而这三类目标互相拉扯：

延迟（用户体验）

第一个 token 多快出来，之后每个 token 隔多久，整条回答多久结束。看的是 p50 / p90 / p99，不是平均值。

吞吐与成本（经济性）

每块 GPU 每秒能产出多少 token，折算成每百万 token 的成本。批越大吞吐越高，但单请求越慢。

质量与可靠性

量化、投机解码、近似 cache 不能让输出变差；服务要可用、可扩缩、能抗突发流量、能隔离租户。

四种典型场景

场景例子最在意可以牺牲
在线交互Chat、Copilot 补全TTFT、TPOT 的 p99，流式输出一部分吞吐（批不能太大）
Agent / 长上下文编码 agent、多轮工具调用、RAG长 prompt 的 prefill 速度、前缀 cache 命中率、端到端完成时间单 token 延迟可略放宽
离线批处理数据合成、评测、Batch API、RL rollout总吞吐、每 token 成本延迟几乎无所谓（RL 例外：长尾会拖慢整个 step）
实时流式语音对话、同传、机器人控制首包延迟、稳定的输出节奏（不能卡顿）、抖动峰值吞吐；常常 batch=1

一个请求的生命周期

以 OpenAI 兼容的 /v1/chat/completions 流式请求为例。前端进程做 HTTP、chat template、tokenize；调度器决定这一步让哪些请求上 GPU；model runner 跑前向；sampler 采样；detokenizer 把 token 变回文本，经 SSE 流回客户端。

核心指标定义

指标全称定义主要受什么影响
TTFTTime To First Token请求到达 → 第一个输出 token 返回。包括排队、prefill、第一次采样。prompt 长度、排队、prefill 算力、前缀 cache 命中
TPOT / ITLTime Per Output Token / Inter-Token LatencyTPOT = (E2E − TTFT)/(n_out − 1)，是单请求的平均值；ITL 是相邻两个 token 的间隔分布，能看出卡顿。decode 批大小、显存带宽、被 prefill 打断
E2E latencyEnd-to-end latency请求到达 → 最后一个 token。≈ TTFT + (n_out − 1) × TPOT。输出长度（推理模型 CoT 很长）
Throughput吞吐输出 token/s、总 token/s（含输入）、请求/s。常按每 GPU 归一化。批大小、kernel 效率、显存能容纳多少并发
Interactivitytokens/s/user单个用户看到的生成速度 = 1/TPOT。和每 GPU 吞吐构成 Pareto 曲线。同上，方向相反
Goodput满足 SLO 的吞吐只统计 TTFT 和 TPOT 都满足 SLO 的请求的吞吐（DistServe 提出的口径）。比裸吞吐更接近“能卖的产能”。尾延迟、P/D 干扰
SLO attainmentSLO 达成率满足 SLO 的请求占比，例如 “99% 请求 TTFT < 2 s 且 TPOT < 50 ms”。负载、调度策略
MFU / MBUModel FLOPs / Bandwidth UtilizationMFU = 实际 FLOP/s ÷ 峰值 FLOP/s（prefill 看它）；MBU = 实际字节/s ÷ 峰值带宽（decode 看它）。kernel 质量、批大小、CPU 开销
$/1M tokens单位成本GPU 小时价 ÷ (每 GPU 每小时产出 token / 10⁶)。输入、输出、缓存命中的输入通常分别计价。吞吐、硬件价格、利用率（空闲时间也要付钱）
其他运营指标排队时间、抢占 / 重算次数、前缀 cache 命中率、KV 使用率、错误率、冷启动时间、可用性。

吞吐和延迟的权衡：Pareto 曲线

decode 一步的耗时近似是 t(B) ≈ t₀ + c·B：t₀ 是把权重读一遍的固定成本，c·B 是随批大小增长的部分（读各自的 KV、计算）。于是批大小 B 越大，每 GPU 吞吐 B/t(B) 越高，但每用户速度 1/t(B) 越低。SemiAnalysis 的 InferenceMAX 等基准就是把这条曲线画出来比较。

两条要背下来的关系式

E2E ≈ TTFT + (n_out − 1) × TPOT 并发数 L = 到达率 λ × 平均停留时间 W # Little's law 例：每秒 20 个请求，每个平均 15 s 才结束 → 系统里稳态约 300 个并发请求，KV cache 要装得下这 300 个
SLO 的常见量级（经验值，因产品而异）
  • 人的阅读速度约 4–8 token/s，所以聊天的 TPOT 在 30–100 ms 之间体验上差别不大；但 agent 和推理模型输出很长，TPOT 直接决定完成时间，所以“每用户速度”越来越受重视。
  • 语音对话要求首包音频在几百毫秒内出来；代码补全要求整段补全几百毫秒内完成。
  • 离线任务的 SLO 是“今晚跑完”，只看成本。

负载画像决定优化方向

  • ISL / OSL（输入 / 输出长度）。RAG、摘要、agent 是长输入短输出（prefill 重）；推理模型（o1 / R1 类）是短输入长输出（decode 重）。基准测试一定要说明长度分布。
  • 前缀共享。系统 prompt、few-shot、多轮对话历史、agent 的工具定义，都让大量请求共享前缀 → 前缀 cache 命中率可以很高（官方 API 对 cached input 打折就是这个原因）。
  • 到达模式。泊松到达 vs 突发；闭环（固定并发，发完一个再发下一个）vs 开环（按速率发）。闭环测试会掩盖排队问题。
  • 多轮与会话。同一会话的下一轮要能找到上一轮的 KV，这影响路由（会话粘性 / KV 感知路由）。

02物理限制：为什么 LLM 推理难

所有优化技术都是在和下面几条硬约束周旋。面试里能把这几条讲清楚并给出数量级，比背技术名词有用得多。

限制 1：自回归，token 只能一个一个生成

第 t+1 个 token 依赖第 t 个 token 的采样结果，所以 decode 无法在时间维度并行。一个 1000 token 的回答至少要 1000 次串行前向。并行只能来自三处：同时服务多个请求（批）、一次猜多个 token 再验证（投机解码）、或者换模型（多 token 预测、扩散 LM）。

限制 2：prefill 吃算力，decode 吃带宽

一次前向对每个参数大约做 2 次浮点运算（乘 + 加）。设权重 BF16（每参数 2 字节），处理 n 个 token：

FLOPs ≈ 2 × N_params × n 读权重字节 ≈ 2 × N_params 算术强度 (arithmetic intensity) ≈ FLOPs / Bytes ≈ n # 单位 FLOP/byte，只算权重 H100 SXM：BF16 稠密峰值 ≈ 989 TFLOP/s，HBM3 带宽 ≈ 3.35 TB/s 脊点 (ridge point) ≈ 989e12 / 3.35e12 ≈ 295 FLOP/byte → 一次前向里同时处理的 token 数 n < ~300 时受带宽限制，> ~300 时受算力限制
  • Prefill：一个 2000 token 的 prompt 一次前向就处理 2000 个 token，强度远超脊点，是 compute-bound。
  • Decode：每个请求每步只处理 1 个 token。批大小 B 的 decode 对权重的强度约为 B，B 不到几百就是 memory-bound。更糟的是 attention 部分要读每个请求自己的 KV cache，这部分不能被批摊薄，强度始终约为 1。
  • 推论：decode 的 batch=1 速度上限 ≈ 带宽 / 权重字节。8B 模型 BF16 约 16 GB，H100 上每步 ≥ 4.8 ms，即单流最多约 200 token/s（还没算 KV）。

限制 3：KV cache 吃显存，而且随并发和上下文线性增长

为了不重复计算历史 token，每层的 Key / Value 要缓存下来。每个 token 的 KV 大小：

KV bytes / token = 2 (K和V) × n_layers × n_kv_heads × head_dim × bytes_per_elem 总 KV = 上式 × Σ 每个并发请求的 (输入 + 已生成) token 数
模型结构每 token KV（BF16）一个 32k 上下文的请求
Llama-3-8B32 层，GQA 8 个 KV head，head_dim 1282×32×8×128×2 = 128 KiB4 GiB
Llama-3-70B80 层，GQA 8 KV head，head_dim 128320 KiB10 GiB
Qwen3-30B-A3B48 层，GQA 4 KV head，head_dim 12896 KiB3 GiB

限制 4：互联带宽比显存带宽低一到两个数量级

模型放不进一张卡就要切分，而切分后的通信走的链路越来越慢。设计并行策略的原则是：通信最频繁的切分（TP）放在最快的链路（NVLink）里。

NVLink（机内）H100 NVLink4 约 450 GB/s 单向（900 GB/s 双向）；Blackwell NVLink5 翻倍TP 的 all-reduce、机内 EP

限制 5：负载不可预测

  • 输出长度事先未知：调度器不知道一个请求会占多久显存，所以要么保守预留（浪费），要么允许超卖再抢占（复杂）。
  • 请求异构：10 个 token 的问候和 100k token 的代码库分析混在一个批里。
  • 流量突发：GPU 扩容是分钟级（拉镜像、加载几百 GB 权重），流量变化是秒级。

限制 6：其他常被忽视的瓶颈

  • CPU 开销：Python 调度、构造输入张量、kernel launch。decode 一步 GPU 只要几毫秒，CPU 慢 1 ms 就是十几个百分点的损失。这是 CUDA graph、多进程架构、调度与计算重叠的动机。
  • 尾延迟：一个长 prompt 进来，整个批的 ITL 都受影响。
  • 数值非确定性：同一请求在不同批大小下结果可能不同（浮点加法不满足结合律、kernel 按批大小选不同切分）。RL 训练和评测对此很敏感，见 08。
  • 功耗与成本：大规模部署时电力和机柜才是上限，单位是“每瓦 token 数”。
