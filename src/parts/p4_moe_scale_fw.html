MoE：模型特征 → 场景 → 推理负载

模型特征为什么这样设计（场景决定）在推理负载上的体现
稀疏激活：每 token 只用 top-k 个专家在固定的训练与推理 FLOPs 下扩大参数量（知识容量）计算按激活参数、显存按总参数；decode 仍要读几乎全部专家权重，但每个专家只分到很少 token → 小而碎的 GEMM
细粒度专家（256、384 个）+ 共享专家细粒度提高专业化程度，共享专家承载通用知识每层两次 all-to-all；热门专家导致负载不均 → EPLB 冗余专家；共享专家可本地计算并与通信重叠
MLA（DeepSeek、Kimi）长上下文 + 高并发需要极小的 KVKV 小 → 单卡可放更多请求，配合 DP attention 进一步放大 EP 下每专家的批
MTP 模块训练时提供更密的监督信号推理时直接当 draft 做投机解码
原生 FP8 训练（块级 scale）降低训练成本推理直接使用 FP8 权重与块级 scale GEMM（DeepGEMM），无需额外量化

MoE 让推理更难的地方

  • 显存：671B 参数 FP8 也要约 700 GB，至少要 8×H200 或跨机。所有专家都要常驻显存，因为任何 token 都可能路由到任何专家。
  • decode 时专家 GEMM 极小：批里 B 个 token，每个选 k 个专家，平均每个专家只分到 B·k/E 个 token。DeepSeek-V3 在 B=64 时：被激活的专家数 ≈ E·(1−(1−k/E)^B) ≈ 222 个（几乎全部），平均每个专家只有约 2.3 个 token。结果是几乎要读全部专家权重，却每个只做极小的矩阵乘 —— 严重 memory-bound。
  • 通信：专家分在不同 GPU 上，每个 MoE 层要两次 all-to-all（dispatch 把 token 发给专家，combine 把结果收回），延迟敏感且量大。
  • 负载不均：热门专家所在的 GPU 成为瓶颈，整个层等最慢的那张卡。训练时可以用 capacity factor 丢 token，推理时不能丢。
关键洞察：用“宽 EP”把每专家批做大

如果把 256 个专家分到 128 张卡上，每张卡只放 2 个专家：显存省下来放 KV（并发更多），同时全局所有请求的 token 会汇聚到少数专家上，每个专家的有效批变大，GEMM 回到高效区。这就是 DeepSeek 推理系统的核心思路：attention 用数据并行（DP，每卡处理自己的请求），MoE 用大规模专家并行（EP）。

案例：DeepSeek-V3/R1 的线上推理系统

DeepSeek 在 2025 年 2 月的 Open Infra 周最后一天公开了线上系统概况，是面试中讲 MoE serving 最好的例子：

  • PD 分离 + 不同并行度：prefill 阶段每个部署单元 4 个节点（32 卡），路由专家 EP32、MLA 与共享专家 DP32；decode 阶段每单元 18 个节点（144 卡），EP144、DP144。
  • 重叠：prefill 用双微批重叠，decode 把 attention 切成两段做 5 级流水的重叠。
  • 负载均衡：prefill、decode 和 attention 各有自己的均衡器（专家冗余、按 KV 使用量与请求数分配请求）。
  • 结果（公开数字，H800）：平均每节点 prefill 约 73.7k token/s（含 cache 命中）、decode 约 14.8k token/s；理论成本利润率 545%。
  • SGLang 团队随后在 96 张 H100 上用 PD 分离 + 大规模 EP 开源复现，2k 输入时每节点约 52.3k 输入 token/s、22.3k 输出 token/s。
阅读 DeepSeek 推理系统概览 ↗ SGLang 大规模 EP 博客 ↗ DeepEP ↗ DeepGEMM ↗ EPLB ↗

机柜级硬件（GB200 / GB300 NVL72）把 72 卡放进一个 NVLink 域，宽 EP 的 all-to-all 可以完全走 NVLink，是当前超大 MoE 部署的主流形态。

06扩展到大规模集群

单个引擎实例优化到头之后，问题变成集群层面的：几百上千张 GPU、多个模型、PD 两个池、跨机实例、流量波动、硬件故障。这一层的软件叫 orchestration / control plane，它不替代 vLLM / SGLang，而是管理一群引擎实例。

路由：命中率和负载均衡的权衡

源码{{s:ai-dynamo/dynamo:lib/llm/src/kv_router|Dynamo kv_router}}{{s:ai-dynamo/dynamo:lib/kv-router/src|Dynamo kv-router crate}}{{s:llm-d/llm-d-router:pkg/epp|llm-d EPP（选实例）}}{{s:sgl-project/sglang:sgl-model-gateway/src|SGLang Model Gateway (Rust)}}{{s:vllm-project/aibrix:pkg/plugins/gateway|AIBrix gateway}}{{r:kubernetes-sigs/gateway-api-inference-extension|Gateway API Inference Ext.}}
  • 轮询 / 最少连接会把同一会话打散到不同实例，前缀 cache 几乎失效。
  • 会话粘性 / 一致性哈希提高命中，但热点会把某个实例打爆。
  • KV 感知路由：路由器维护每个实例缓存了哪些 block（通过引擎上报的 KV 事件，或近似 radix tree），对每个候选实例算 “命中可省的 prefill 量 − 负载代价”。代表：NVIDIA Dynamo KV Router、llm-d 的 inference scheduler（prefix-cache scorer）、SGLang Model Gateway（原 sgl-router）的 cache-aware 策略、AIBrix router。
  • Kubernetes 标准化：Gateway API Inference Extension 定义了 InferencePool 和 endpoint picker，把“模型感知的选实例”做成 K8s 网关的扩展点，llm-d 等基于它实现。

扩缩容与冷启动

源码{{s:ai-dynamo/dynamo:components/src/dynamo/global_planner|Dynamo planner}}{{s:vllm-project/aibrix:pkg/controller|AIBrix controller}}{{r:vllm-project/production-stack|production-stack}}{{r:kubernetes-sigs/lws|LeaderWorkerSet}}
  • 别用 GPU 利用率当信号：decode 时 nvidia-smi 的 util 几乎总是 100%。应看队列长度、KV 使用率、TTFT / TPOT 的 SLO 违约率。PD 分离时 P 和 D 分开扩（Dynamo Planner 就是做这个）。
  • 冷启动链路：调度 GPU 节点 → 拉镜像（几十 GB）→ 加载权重（几百 GB，从对象存储 → 本地 NVMe → 显存）→ torch.compile / CUDA graph 预热。优化手段：权重预放到节点、并行流式加载（Run:ai Model Streamer、fastsafetensors）、节点间 P2P 分发权重、编译缓存、GPU 进程快照（如 Modal 的 GPU memory snapshot、CUDA checkpoint）。
  • 多模型共用 GPU：vLLM 的 sleep mode（释放权重 / KV 显存，秒级唤醒）、多 LoRA、按需加载，适合长尾模型。

可靠性

  • 一个宽 EP 实例跨 18 个节点时，任意一张卡出错整个实例就挂；需要健康检查、快速剔除、请求重试、专家迁移。
  • 请求迁移：Llumnix（OSDI ’24）在实例间实时迁移请求（连同 KV），用于负载均衡、降级和优雅下线。
  • 流量削峰：Batch API（离线任务，24 小时内完成，通常半价）填平低谷；优先级让在线请求先走。

vLLM

2023 年出自 UC Berkeley Sky Computing Lab（PagedAttention 论文），现为 PyTorch Foundation 托管项目，是模型和硬件覆盖最广的开源引擎。2025 年起 V1 架构成为默认实现。2026 年 1 月核心作者创立 Inferact（a16z、Lightspeed 领投 1.5 亿美元种子轮）做商业化。
