12Coding Agent 的推理：长会话、高命中、慢工具

代码是目前 LLM 商业化最成功的场景之一，但“写代码”背后其实是三种完全不同的推理负载：编辑器内的行内补全、把建议应用到文件的快速编辑（apply），以及自主完成任务的 agentic coding（Claude Code、Codex、Cursor Agent、OpenHands 等）。它们对 serving 的要求差别之大，几乎可以当成三个产品来设计。

模型特征 → 场景 → 推理负载

模型特征为什么这样设计（场景决定）在推理负载上的体现
超长上下文（128k–1M token）要读懂整个仓库、长日志、长 diff；agent 任务一次跑几十上百轮单请求 prompt 常在 50k–200k；KV 显存巨大（70B 级模型 100k 上下文单请求 30 GB 量级）；prefill 是主要算力消耗
工具调用 + 在 SWE 类环境上做 agentic RL模型要自己读文件、改代码、跑测试、看报错再修多轮、追加式上下文：每轮只在末尾追加工具输出，前面全部不变 → 前缀命中率可达 90% 以上，成为最关键的指标；两轮之间有工具执行的“空档”（秒到分钟）
推理（thinking）模式，交错思考与工具调用规划、定位 bug、复杂重构需要先想再做输出也长；agent 循环是串行的，每用户 tokens/s 直接决定任务完成时间，所以 TPOT 比聊天更重要
FIM（fill-in-the-middle）训练的小模型编辑器补全需要看到光标前后的代码补全：输出很短、端到端预算几百毫秒、QPS 极高、大量请求在完成前就被取消（用户继续打字）
代码高度可预测，编辑大量复制原文改代码时大部分内容保持不变投机解码收益特别大：prompt lookup / n-gram 直接从原文件取 draft（“speculative edits”），apply 模型可以跑到每秒上千 token
大 MoE 骨干（Qwen3-Coder、Kimi K2、GLM、DeepSeek、MiniMax 系列等）强能力 + 可控推理成本继承 05 的所有 MoE 部署问题；长上下文让 KV 而不是权重成为显存主体

三种负载的对比

维度行内补全（Tab）快速编辑 / applyAgentic coding
模型小模型（几 B），FIM中小模型，专门训练“改写文件”前沿大模型（常为 MoE），thinking + tool use
输入 / 输出几千 token / 几十 token整个文件 + 修改意图 / 几乎整个文件5 万–20 万 token（逐轮增长）/ 几百到几千 token 每轮
延迟目标端到端几百毫秒以内整文件改写一两秒每轮 TTFT 与 TPOT；整体任务完成时间（分钟级）
关键技术小模型 + 低延迟部署、请求取消、边缘 / 近端部署、前缀 cache（同文件反复请求）投机解码（原文件作 draft）、高 tokens/s前缀 cache 与 KV 分层存储、会话粘性 / KV 感知路由、长上下文 kernel、tool-call 解析、sandbox 编排、上下文压缩（compaction）
计费与成本按席位按 token缓存命中的输入远便宜于未命中；命中率直接决定毛利

Serving 侧的具体做法

  • 把命中率当一等指标。监控 per-session 的 cached-token 比例；路由用会话 ID 或前缀哈希做粘性，再叠加负载感知（06 的 KV 感知路由）。商业 API 的 prompt caching（例如 Anthropic 默认 5 分钟、可选 1 小时 TTL 的缓存）就是把“工具空档里保留 KV”这件事产品化。
  • KV 的生命周期跨越工具调用。GPU 上用 LRU 保留，压力大时下沉到 CPU / SSD（LMCache、HiCache、Mooncake、Dynamo KVBM）；按 4.2 的估算，载回远比重算便宜。
  • 长上下文 prefill 的成本控制：chunked prefill 防止一个 200k prompt 卡住别人；必要时用上下文并行；agent 侧做上下文压缩、子 agent 拆分任务，减少单会话上下文长度。
  • 可靠的工具调用：每个模型家族的 tool-call 格式不同，引擎里的 tool parser / reasoning parser 必须和模型模板严格匹配；必要时用结构化输出约束参数 JSON。
  • Sandbox 是推理链路的一部分：每个会话一个隔离环境（容器 / microVM），要快速创建、可暂停恢复、可快照；训练（agentic RL）和线上用的是同一套。阿里开源的 OpenSandbox 就是面向 coding agent、GUI agent、评测和 RL 的通用 sandbox 平台（Docker / Kubernetes 运行时，多语言 SDK，内置 MCP server），见 14。
  • 评测：SWE-bench 系列（真实仓库 issue → 补丁 → 在容器里跑测试）、Terminal-Bench 等；评测本身就是“推理 + 大量 sandbox”的负载。

13AI for Science 的推理：结构、几何与物理

科学模型的输入不是自然语言，而是蛋白质序列与多序列比对、原子坐标、基因组、全球气象网格。这些数据的结构决定了模型结构（成对表示、等变网络、图网络、超长卷积），进而让推理负载和 LLM serving 很不一样：batch 往往为 1、显存随问题规模平方增长、CPU 侧预处理可能比 GPU 推理还慢、对数值精度更敏感、大量是离线批量筛选。

模型特征 → 场景 → 推理负载

模型特征为什么这样设计（科学问题决定）在推理负载上的体现
蛋白 / 复合物结构预测（AlphaFold2/3、OpenFold、Boltz、Chai-1、Protenix）：维护 N×N×c 的成对表示，用三角乘法 / 三角注意力更新结构本质是残基两两之间的几何关系，三角更新近似强制“三角不等式”一致性显存随残基数 平方增长，三角注意力计算接近 立方；几千残基的复合物就会爆显存 → 分块（chunking）、低精度、专用三角注意力 kernel；每个复合物单独推理，batch≈1，形状各不相同（难以 CUDA graph）
以 MSA（多序列比对）和模板为输入同源序列的共进化信号揭示哪些残基在空间上接触推理前要在 TB 级序列库上做 jackhmmer / HHblits 搜索，CPU 小时级，常常比 GPU 推理慢得多 → MMseqs2（ColabFold）加速、MSA 缓存与共享服务、GPU 加速搜索
AF3 类模型的扩散结构模块 + 多 seed 采样与置信度排序全原子（蛋白、核酸、小分子、离子）生成，需要多样本评估置信度一次预测 = 主干一次 + 扩散几百步 × 多个样本 → 吞吐与延迟都看扩散部分；可以像 10 一样批量化多个样本
蛋白 / DNA 语言模型（ESM-2/ESM3、Evo 2）：Transformer 或卷积–注意力混合（Evo 2 的 StripedHyena 2），上下文最长到百万碱基基因组有长程调控关系；进化数据量巨大，适合自监督最像 LLM 的科学负载：主要是批量 embedding / 打分（整个蛋白组、变异效应评分）而不是交互生成 → 吞吐优先、离线；长序列需要长卷积 / 上下文并行 kernel
天气 / 气候模型（GraphCast：网格上的 GNN；FourCastNet：频域算子；GenCast：扩散集合预报）全球格点、物理场之间的相互作用；预报本身是概率性的自回归滚动几十步（例如 6 小时一步滚 10 天）；集合预报要几十个成员 → 天然的批；输入输出是 TB 级再分析数据，I/O 与数据管线常是瓶颈；需要在 HPC 定时批量运行
机器学习原子势（MLIP）（MACE、NequIP / Allegro、Meta 的 UMA）：E(3) 等变图网络，球谐与张量积物理量在旋转 / 平移下必须正确变换（能量不变，力等变），保证分子动力学稳定嵌在分子动力学循环里跑百万步，每步一个小图（几百到几千原子）→ 延迟与 kernel launch 主导；等变张量积 kernel 是热点（cuEquivariance）；常要求 FP32 甚至 FP64 精度，BF16 可能破坏能量守恒
科研 agent（文献、实验规划、调用仿真工具）把 LLM 当作科研助理本质上和 12 的 coding agent 一样：长上下文、多轮工具调用、sandbox 执行代码

与 LLM serving 的差异总结

维度LLM servingAI for Science 推理
批处理continuous batching，几百并发常为 batch=1（结构预测、MD）；或天然大批（集合预报、蛋白组 embedding、虚拟筛选）
形状变长但每 token 计算相同问题规模差别巨大（几十到几千残基），显存按 N² 增长，常需按大小分桶 / 分配不同显存的卡
瓶颈decode 带宽成对表示的显存、三角运算、CPU 预处理（MSA）、数据 I/O、小图上的 launch 开销
精度FP8 / FP4 已普遍BF16 / TF32 为主，MLIP 等可能需要 FP32 / FP64；可重复性要求高
部署形态在线 APIHPC 批作业（Slurm）、科研平台的异步任务、少量在线服务（如 AlphaFold Server、NVIDIA BioNeMo NIM）
专用 kernelattention、GEMM、MoE三角注意力 / 三角乘法、带 pair bias 的 attention、等变张量积、球谐、图的 scatter / gather、FFT
  • 优化手段：主干分块与 activation offload；三角注意力 kernel（NVIDIA cuEquivariance 提供 triangle attention / multiplication，DeepSpeed4Science 有 Evoformer attention）；MSA 搜索 GPU 化与缓存；扩散样本批量化；MLIP 用 CUDA graph 和融合的等变 kernel 降低每步延迟，并与 LAMMPS / ASE 等 MD 引擎原生集成。
  • 服务化：NVIDIA BioNeMo（框架与 NIM 微服务，覆盖结构预测、蛋白 / 基因组语言模型）、Google DeepMind 的 AlphaFold Server、ColabFold 的公共 MSA 服务、NVIDIA Earth2Studio（天气模型推理与集合预报流水线）、ECMWF 的 AI 预报业务化运行。
