01推理服务本身：要求与指标

Inference serving 的任务是把训练好的模型变成一个服务：接收请求、在加速器上跑前向、把结果（常常是流式地）返回。它要同时满足三类目标，而这三类目标互相拉扯：

延迟（用户体验）

第一个 token 多快出来，之后每个 token 隔多久，整条回答多久结束。看的是 p50 / p90 / p99，不是平均值。

吞吐与成本（经济性）

每块 GPU 每秒能产出多少 token，折算成每百万 token 的成本。批越大吞吐越高，但单请求越慢。

质量与可靠性

量化、投机解码、近似 cache 不能让输出变差；服务要可用、可扩缩、能抗突发流量、能隔离租户。

四种典型场景

场景例子最在意可以牺牲
在线交互Chat、Copilot 补全TTFT、TPOT 的 p99，流式输出一部分吞吐（批不能太大）
Agent / 长上下文编码 agent、多轮工具调用、RAG长 prompt 的 prefill 速度、前缀 cache 命中率、端到端完成时间单 token 延迟可略放宽
离线批处理数据合成、评测、Batch API、RL rollout总吞吐、每 token 成本延迟几乎无所谓（RL 例外：长尾会拖慢整个 step）
实时流式语音对话、同传、机器人控制首包延迟、稳定的输出节奏（不能卡顿）、抖动峰值吞吐；常常 batch=1

一个请求的生命周期

以 OpenAI 兼容的 /v1/chat/completions 流式请求为例。前端进程做 HTTP、chat template、tokenize；调度器决定这一步让哪些请求上 GPU；model runner 跑前向；sampler 采样；detokenizer 把 token 变回文本，经 SSE 流回客户端。

吞吐和延迟的权衡：Pareto 曲线

decode 一步的耗时近似是 t(B) ≈ t₀ + c·B：t₀ 是把权重读一遍的固定成本，c·B 是随批大小增长的部分（读各自的 KV、计算）。于是批大小 B 越大，每 GPU 吞吐 B/t(B) 越高，但每用户速度 1/t(B) 越低。SemiAnalysis 的 InferenceMAX 等基准就是把这条曲线画出来比较。

两条要背下来的关系式

E2E ≈ TTFT + (n_out − 1) × TPOT 并发数 L = 到达率 λ × 平均停留时间 W # Little's law 例：每秒 20 个请求，每个平均 15 s 才结束 → 系统里稳态约 300 个并发请求，KV cache 要装得下这 300 个
SLO 的常见量级（经验值，因产品而异）
  • 人的阅读速度约 4–8 token/s，所以聊天的 TPOT 在 30–100 ms 之间体验上差别不大；但 agent 和推理模型输出很长，TPOT 直接决定完成时间，所以“每用户速度”越来越受重视。
  • 语音对话要求首包音频在几百毫秒内出来；代码补全要求整段补全几百毫秒内完成。
  • 离线任务的 SLO 是“今晚跑完”，只看成本。

负载画像决定优化方向

  • ISL / OSL（输入 / 输出长度）。RAG、摘要、agent 是长输入短输出（prefill 重）；推理模型（o1 / R1 类）是短输入长输出（decode 重）。基准测试一定要说明长度分布。
  • 前缀共享。系统 prompt、few-shot、多轮对话历史、agent 的工具定义，都让大量请求共享前缀 → 前缀 cache 命中率可以很高（官方 API 对 cached input 打折就是这个原因）。
  • 到达模式。泊松到达 vs 突发；闭环（固定并发，发完一个再发下一个）vs 开环（按速率发）。闭环测试会掩盖排队问题。
  • 多轮与会话。同一会话的下一轮要能找到上一轮的 KV，这影响路由（会话粘性 / KV 感知路由）。

02物理限制：为什么 LLM 推理难

所有优化技术都是在和下面几条硬约束周旋。面试里能把这几条讲清楚并给出数量级，比背技术名词有用得多。

限制 1：自回归，token 只能一个一个生成

第 t+1 个 token 依赖第 t 个 token 的采样结果，所以 decode 无法在时间维度并行。一个 1000 token 的回答至少要 1000 次串行前向。并行只能来自三处：同时服务多个请求（批）、一次猜多个 token 再验证（投机解码）、或者换模型（多 token 预测、扩散 LM）。

限制 2：prefill 吃算力，decode 吃带宽

一次前向对每个参数大约做 2 次浮点运算（乘 + 加）。设权重 BF16（每参数 2 字节），处理 n 个 token：

FLOPs ≈ 2 × N_params × n 读权重字节 ≈ 2 × N_params 算术强度 (arithmetic intensity) ≈ FLOPs / Bytes ≈ n # 单位 FLOP/byte，只算权重 H100 SXM：BF16 稠密峰值 ≈ 989 TFLOP/s，HBM3 带宽 ≈ 3.35 TB/s 脊点 (ridge point) ≈ 989e12 / 3.35e12 ≈ 295 FLOP/byte → 一次前向里同时处理的 token 数 n < ~300 时受带宽限制，> ~300 时受算力限制
  • Prefill：一个 2000 token 的 prompt 一次前向就处理 2000 个 token，强度远超脊点，是 compute-bound。
  • Decode：每个请求每步只处理 1 个 token。批大小 B 的 decode 对权重的强度约为 B，B 不到几百就是 memory-bound。更糟的是 attention 部分要读每个请求自己的 KV cache，这部分不能被批摊薄，强度始终约为 1。
  • 推论：decode 的 batch=1 速度上限 ≈ 带宽 / 权重字节。8B 模型 BF16 约 16 GB，H100 上每步 ≥ 4.8 ms，即单流最多约 200 token/s（还没算 KV）。

限制 3：KV cache 吃显存，而且随并发和上下文线性增长

为了不重复计算历史 token，每层的 Key / Value 要缓存下来。每个 token 的 KV 大小：

KV bytes / token = 2 (K和V) × n_layers × n_kv_heads × head_dim × bytes_per_elem 总 KV = 上式 × Σ 每个并发请求的 (输入 + 已生成) token 数

限制 4：互联带宽比显存带宽低一到两个数量级

模型放不进一张卡就要切分，而切分后的通信走的链路越来越慢。设计并行策略的原则是：通信最频繁的切分（TP）放在最快的链路（NVLink）里。

限制 5：负载不可预测

  • 输出长度事先未知：调度器不知道一个请求会占多久显存，所以要么保守预留（浪费），要么允许超卖再抢占（复杂）。
  • 请求异构：10 个 token 的问候和 100k token 的代码库分析混在一个批里。
  • 流量突发：GPU 扩容是分钟级（拉镜像、加载几百 GB 权重），流量变化是秒级。

限制 6：其他常被忽视的瓶颈

  • CPU 开销：Python 调度、构造输入张量、kernel launch。decode 一步 GPU 只要几毫秒，CPU 慢 1 ms 就是十几个百分点的损失。这是 CUDA graph、多进程架构、调度与计算重叠的动机。
  • 尾延迟：一个长 prompt 进来，整个批的 ITL 都受影响。
  • 数值非确定性：同一请求在不同批大小下结果可能不同（浮点加法不满足结合律、kernel 按批大小选不同切分）。RL 训练和评测对此很敏感，见 08。
  • 功耗与成本：大规模部署时电力和机柜才是上限，单位是“每瓦 token 数”。

4.1 批处理与调度：continuous batching

源码vLLM scheduler.pyvLLM engine/core.pypersistent batchSGLang scheduler.pyschedule_policy.pyschedule_batch.pyTRT-LLM py_executor

解决 P2、P3。朴素的静态批（static batching）把 N 个请求凑成一批，直到最长的那个结束才能换下一批。Orca（OSDI ’22）提出 iteration-level scheduling：调度粒度从“一个请求”降到“一次前向迭代”，每一步结束后，完成的请求立刻退出、等待的请求立刻补进来。这就是 continuous batching（也叫 in-flight batching）。

和 continuous batching 配套的几件事

  • Selective batching / 扁平化。线性层（QKV 投影、MLP）不关心 token 属于哪个请求，把所有请求的 token 拼成一个 [总 token 数, hidden] 张量一起算，没有 padding；只有 attention 按请求分开（varlen / paged attention kernel）。
  • Token budget。每步最多处理 max_num_batched_tokens 个 token、最多 max_num_seqs 个请求，控制单步时长和激活显存。vLLM V1 把 prefill 和 decode 统一看成“给每个请求分配本步要算的 token 数”，于是 chunked prefill、前缀 cache、投机解码都落在同一套逻辑里。
  • 抢占（preemption）。KV 不够时把某些请求踢出：recompute（丢掉 KV，之后重新 prefill，vLLM 默认）或 swap（KV 拷到 CPU 内存）。抢占频繁说明并发超过了 KV 容量。
  • 调度策略。FCFS 最常见；还有优先级调度、公平调度（如 OSDI ’24 的 VTC，按租户已服务 token 数做公平）、按预测输出长度排序（近似最短作业优先，降低平均延迟）、SLO 感知调度。SGLang 还有 cache-aware 调度：优先调度前缀命中长的请求。

4.2 KV cache 管理：PagedAttention、前缀缓存、分层存储

PagedAttention（vLLM，SOSP ’23）

源码kv_cache_manager.pyblock_pool.pysingle_type_kv_cache_manager.pycache_kernels.cuSGLang memory_pool.py

解决 P1，间接解决 P3。借鉴操作系统的虚拟内存分页：KV 被切成固定大小的 block（默认 16 个 token），每个请求有一张 block table 把逻辑 block 映射到任意位置的物理 block，按需分配。浪费只剩每个请求最后一个没填满的 block。论文报告已有系统浪费 60–80% 的 KV 显存，vLLM 降到 4% 以下，吞吐提升 2–4 倍。分页还让共享变得容易：并行采样、beam search 的公共前缀只存一份，靠引用计数 + copy-on-write。

前缀缓存：vLLM APC 与 SGLang RadixAttention

源码vLLM block 哈希 kv_cache_utils.pySGLang radix_cache.py

解决 P5。请求结束后不立刻释放 KV，而是留作 cache；新请求如果前缀相同就直接复用，只 prefill 不同的部分，TTFT 和算力都省下来。两种主流实现：

vLLM Automatic Prefix Caching

以满 block 为单位，每个 block 的 key = hash(父 block 的 hash, 本 block 的 token, 额外信息如 LoRA / 多模态 hash)。全局哈希表查找；引用计数为 0 的 block 进入 LRU 空闲队列，被复用前仍可命中。实现简单、开销 O(1)。

SGLang RadixAttention

把所有缓存的 token 序列组织成一棵 radix tree（压缩前缀树），边上是 token 序列，节点挂着对应的 KV。匹配就是从根往下走最长前缀；淘汰按 LRU 从叶子开始。配合 cache-aware 调度（优先最长前缀匹配），对多轮对话、few-shot、tree-of-thought 等复杂共享模式很友好。

KV 分层存储与 offload

源码vLLM kv_offload/SGLang hicache_storage.pyLMCacheMooncake StoreDynamo kv_router

解决 P5、P10。GPU 显存装不下所有值得缓存的前缀（多轮对话、agent 的长上下文、多副本之间的共享），于是把 KV 下沉到 CPU 内存、本地 SSD、甚至远端分布式存储，命中时再载回。判断是否值得的数量级：

Llama-3-8B，10k token 前缀：KV = 10k × 128 KiB ≈ 1.25 GiB 从 CPU 载回（PCIe Gen5，约 50 GB/s 实际）：≈ 25 ms 重新 prefill：2 × 8e9 × 1e4 = 1.6e14 FLOP，按 600 TFLOP/s 有效算力 ≈ 270 ms → 载回比重算快约 10 倍；上下文越长、模型越大，差距越大
  • 开源实现：LMCache（vLLM 生态的 KV 存储层，CPU / 磁盘 / 远端后端）、Mooncake Store（Kimi 的 KVCache-centric 架构，利用集群空闲的 CPU 内存和 SSD，RDMA 传输）、SGLang HiCache（GPU → CPU → 存储三级 radix cache）、NVIDIA Dynamo KVBM（KV block manager）。
  • 商业 API 的体现：DeepSeek 的上下文硬盘缓存、Anthropic / OpenAI 的 prompt caching（命中部分价格大幅打折）。
  • KV 量化（FP8 / INT8）也是一种“扩容”：容量翻倍、attention 读带宽减半，通常精度损失很小。

4.3 Chunked prefill：把 prefill 切碎塞进 decode 批

源码vLLM：token budget 内拆分 prefillSGLang：PrefillAdder 与 chunked req

解决 P4。长 prompt 的 prefill 一次要跑几百毫秒，期间同一 GPU 上所有 decode 请求都停住，ITL 出现尖峰。Sarathi-Serve（OSDI ’24）把 prefill 切成固定大小的 chunk，每次迭代 = 所有 decode token + 一个 prefill chunk，凑满 token budget。这样 decode 永不被长时间阻塞（stall-free），而 prefill chunk 正好把 decode 批“吃不饱”的算力用掉。

  • 权衡：chunk 越小，ITL 越平稳，但 prefill 效率下降（每个 chunk 要重读之前 chunk 的 KV、GEMM 变小），X 自己的 TTFT 变长。常见 token budget 是 2k–8k，根据 TPOT SLO 调。
  • 与 PD 分离的关系：chunked prefill 是“同一 GPU 内做时间上的隔离”，PD 分离是“换不同 GPU 做空间上的隔离”。中小规模部署用 chunked prefill 通常就够了；它在 vLLM V1 中默认开启。

4.4 Prefill–Decode 分离（PD disaggregation）

源码vLLM KVConnector 接口NixlConnectorLMCacheConnectorSGLang PD prefill.pydecode.pymooncake/conn.pyNIXL APIMooncake Transfer Engine

解决 P4，并让两阶段可以独立选并行度、硬件和扩缩容。prefill 是 compute-bound、关心 TTFT；decode 是 memory-bound、关心 TPOT 和大批。放在一起时，无论怎么调度都在两个 SLO 之间妥协。DistServe（OSDI ’24）、Splitwise（ISCA ’24）、Mooncake（FAST ’25）把它们放到不同的 GPU 池，prefill 算完后把 KV cache 通过 RDMA / NVLink 传给 decode 实例。DistServe 报告在同样 SLO 下最多可服务 7.4 倍的请求。

收益

  • TTFT 与 TPOT 解耦，各自满足 SLO，goodput 提升。
  • 两池可以用不同并行度：prefill 用 TP 降 TTFT，decode 用大 DP + 宽 EP 撑大批（DeepSeek 就是这样，见 05）。
  • P:D 比例按负载独立扩缩（长 prompt 多就多加 P）。
  • 可以用不同硬件（如算力强的卡做 P，显存带宽大的卡做 D）。

代价与适用条件

  • 要传 KV：70B 模型 4k prompt 约 1.25 GiB；单张 400G 网卡约 25 ms，8 卡并行约 3 ms。需要 RDMA 和逐层流水才能藏住。
  • 系统复杂：两套实例、路由、失败处理、KV 生命周期。
  • 小模型、短 prompt、小集群时收益有限，chunked prefill 更划算。
  • 实现：vLLM 的 KV Connector 抽象（NixlConnector、LMCacheConnector、P2pNcclConnector、Mooncake 等），SGLang 的 PD 模式（Mooncake / NIXL 传输后端 + bootstrap 握手），NVIDIA Dynamo 和 llm-d 在集群层编排 PD。
  • 进一步的拆分：EPD（把多模态 encoder 也拆出去，见 09）、AF 分离（attention 与 FFN/专家分到不同 GPU，例如字节的 MegaScale-Infer、阶跃星辰 Step-3 的 AFD），本质都是“按算力特征把模型的不同部分放到最合适的资源上”。

4.5 投机解码（Speculative decoding）

源码vLLM eagle.pyngram_proposer.pyrejection_sampler.pySGLang eagle_worker_v2.pyEAGLE 官方Medusa

解决 P6。decode 小批时 GPU 算力大量闲置，验证 k 个 token 的成本和生成 1 个几乎一样（都是读一遍权重）。于是：用便宜的方法先猜 k 个 token（draft），再让目标模型一次前向并行验证，接受最长的正确前缀，外加目标模型在第一个拒绝位置自己采样出的一个 token。用拒绝采样（rejection sampling）做接受判断时，输出分布与目标模型完全一致（Leviathan et al. 2022；Chen et al. 2023）。

每次验证期望前进的 token 数 = (1 − α^(k+1)) / (1 − α) # α = 每个 draft token 的接受率，k = draft 长度 例：α = 0.8, k = 4 → (1 − 0.8⁵)/0.2 ≈ 3.36 个 token / 次目标前向 实际加速 = 期望 token 数 ÷ (1 + draft 开销占比 + 验证比单 token 多出的开销)

稀疏激活：每 token 只用 top-k 个专家在固定的训练与推理 FLOPs 下扩大参数量（知识容量）计算按激活参数、显存按总参数；decode 仍要读几乎全部专家权重，但每个专家只分到很少 token → 小而碎的 GEMM
细粒度专家（256、384 个）+ 共享专家细粒度提高专业化程度，共享专家承载通用知识每层两次 all-to-all；热门专家导致负载不均 → EPLB 冗余专家；共享专家可本地计算并与通信重叠

MoE 让推理更难的地方

  • 显存：671B 参数 FP8 也要约 700 GB，至少要 8×H200 或跨机。所有专家都要常驻显存，因为任何 token 都可能路由到任何专家。
  • decode 时专家 GEMM 极小：批里 B 个 token，每个选 k 个专家，平均每个专家只分到 B·k/E 个 token。DeepSeek-V3 在 B=64 时：被激活的专家数 ≈ E·(1−(1−k/E)^B) ≈ 222 个（几乎全部），平均每个专家只有约 2.3 个 token。结果是几乎要读全部专家权重，却每个只做极小的矩阵乘 —— 严重 memory-bound。
  • 通信：专家分在不同 GPU 上，每个 MoE 层要两次 all-to-all（dispatch 把 token 发给专家，combine 把结果收回），延迟敏感且量大。
  • 负载不均：热门专家所在的 GPU 成为瓶颈，整个层等最慢的那张卡。训练时可以用 capacity factor 丢 token，推理时不能丢。
关键洞察：用“宽 EP”把每专家批做大

如果把 256 个专家分到 128 张卡上，每张卡只放 2 个专家：显存省下来放 KV（并发更多），同时全局所有请求的 token 会汇聚到少数专家上，每个专家的有效批变大，GEMM 回到高效区。这就是 DeepSeek 推理系统的核心思路：attention 用数据并行（DP，每卡处理自己的请求），MoE 用大规模专家并行（EP）。

案例：DeepSeek-V3/R1 的线上推理系统

DeepSeek 在 2025 年 2 月的 Open Infra 周最后一天公开了线上系统概况，是面试中讲 MoE serving 最好的例子：

08后训练里的推理：RL rollout 是一个推理问题

推理引擎不只用来服务用户，后训练的很多环节本质上都是大批量推理：

  • 在线 RL（PPO、GRPO、DAPO 等）：每一步都要用当前策略为每个 prompt 生成多条回答（GRPO 常见 8–64 条），推理模型的回答动辄上万 token。
  • 数据合成与蒸馏：用强模型批量生成 SFT 数据；rejection sampling / best-of-N 挑选高分样本。
  • 打分：reward model、LLM-as-judge 也是推理负载。
  • 训练中的评测：每隔若干步在基准上跑一遍。

四个核心难题

1. 权重同步

  • Colocated（共置）：训练和推理分时共用同一批 GPU。训练时推理引擎“睡眠”（vLLM sleep mode / SGLang release_memory_occupation 释放 KV 和权重显存），推理时把训练状态 offload。权重通过 CUDA IPC 句柄零拷贝传给推理引擎，并从 FSDP / Megatron 的切分方式 reshard 成推理的 TP 布局。verl 的 HybridEngine 是代表。
  • Disaggregated（分离）：训练和推理各用一组 GPU，权重通过 NCCL / RDMA 广播。资源利用更灵活，适合异步 RL；超大模型要优化传输（例如 Moonshot 开源的 checkpoint-engine 用于万亿参数模型的快速权重更新）。

2. 长尾（straggler）

同步 RL 里，一个 step 必须等最长的回答生成完，其他 GPU 空转。

  • Partial rollout（Kimi k1.5）：超长回答先截断，下一轮接着生成。
  • 异步 / off-policy：AReaL（全异步 + staleness 控制）、verl / slime 的 one-step off-policy、PipelineRL（生成中途更新权重）。
  • 动态采样 / 过采样：DAPO 丢掉奖励全相同（无梯度信号）的组，多发一些 prompt 来凑满批。

3. 训练–推理不一致（training–inference mismatch）

推理引擎算出的 token 概率和训练引擎对同一序列重算的概率不完全一样：kernel 不同、批大小不同导致的归约顺序不同、rollout 用 FP8 而训练用 BF16、MoE 的路由在两边选了不同专家。结果是“名义上的 on-policy 实际上是 off-policy”，会导致训练不稳定甚至崩溃。

  • 训练侧重算 logprob，并用重要性采样修正（如截断重要性采样 TIS）。
  • MoE 路由回放：记录 rollout 时每个 token 用了哪些专家，训练时强制用相同路由。
  • 确定性 / 批不变（batch-invariant）kernel：Thinking Machines 2025 年的文章《Defeating Nondeterminism in LLM Inference》指出非确定性主要来自 kernel 的归约顺序随批大小变化，而不是常说的“GPU 并发”；之后 vLLM 和 SGLang 都加入了确定性推理模式（会损失一些性能）。

4. Agentic RL 的多轮交互

  • 一条轨迹包含多次“生成 → 调工具 → 拿结果 → 再生成”，环境步骤（跑单元测试、编译、浏览网页）可能比生成还慢，需要异步调度，否则 GPU 空等。
  • 需要大量并发 sandbox（几千个隔离的容器 / microVM），见 14。
  • 多轮之间要复用 KV（会话粘性、前缀 cache）；尽量 “token in, token out”，避免每轮把文本重新 tokenize 带来的 token 序列漂移。

09Omni / 语音 / 多模态模型的推理服务

多模态分两类：多模态输入（VLM，图像 / 视频 / 音频 → 文本），基本可以沿用 LLM serving，只多一个 encoder；多模态输出（文本 + 语音、图像生成、any-to-any），模型由多个异构组件串起来，serving 的假设被根本改变。

代表模型的结构：Thinker–Talker

以 Qwen3-Omni 为例：音频 encoder（AuT）和视觉 encoder（SigLIP2）把输入编码后交给 Thinker（30B 总参数 / 3B 激活的 MoE LLM）生成文本；Thinker 的隐藏状态再交给 Talker（3B / 0.3B 激活的 MoE，带 MTP 预测多层 codebook）生成音频 codec token；最后 Code2Wav（约 2 亿参数的卷积网络）把 codec token 解码成波形，按块流式输出。类似结构还有 Qwen2.5-Omni、MiniCPM-o、Ming-Omni 等；全双工模型如 Kyutai 的 Moshi 能边听边说。

Omni / 语音：模型特征 → 场景 → 推理负载

模型特征为什么这样设计（场景决定）在推理负载上的体现
统一的多模态输入（音频 / 视觉 encoder）一个模型理解所有模态encoder 是非自回归的大算子；一张图几百到几千个视觉 token → prefill 变长；encoder 输出可缓存，或拆成独立 encode 池（EPD）
Thinker–Talker 分离文本推理和语音生成需要不同规模的模型，解耦后各自最优一个请求跨多个异构阶段，每个阶段的批大小与资源不同；阶段间要传隐藏状态
离散音频 codec：多 codebook（RVQ），每秒十几到几十帧用语言模型的方式生成音频每秒音频需要几十次 Talker decode × 多个 codebook → 小模型、超高频 decode，launch 开销占比高，需要 CUDA graph / MTP 一次预测多层
因果、可流式的 codec 解码器实时对话chunk 级流水；首包延迟（TTFP）和 RTF < 1 成为硬约束
全双工（边听边说）自然的对话体验、可打断持久会话 + 固定节拍推进 + 打断时取消；调度从“吞吐优先”变成“实时优先”

相对 LLM serving，哪些假设变了

级联 vs 端到端

级联：ASR → LLM → TTS

扩散的 serving 系统设计

  • 异步任务 API：生成要数十秒，通常是“提交 → 轮询 / webhook / 流式进度”，而非长连接等待。
  • 请求级 vs 步级批处理：每一步跑的是同一个网络，不同请求处在不同步也能拼批（step-level continuous batching）；要求分辨率 / 帧数相同或做分桶。vLLM-Omni 等已实现扩散的连续批处理。
  • LoRA 热切换：图像平台上用户大量使用风格 LoRA，需要快速加载与融合。
  • 流水线解耦：文本 encoder、DiT、VAE 可以放不同 GPU / 不同批大小（AR + DiT 混合模型更需要，如 HunyuanImage-3、BAGEL）。
  • 与 LLM 技术融合：自回归视频扩散（CausVid、Self-Forcing）按帧块生成并缓存 KV，能实时流式出视频；交互式世界模型（如 Genie 3、Cosmos 类）把扩散推理变成了“流式 + KV cache + 低延迟”的问题。扩散语言模型（LLaDA、Mercury、Gemini Diffusion）则把并行去噪带到了文本生成。

关键技术

  • Action chunking（ACT，2023）：一次推理预测未来 H 步动作，降低推理频率要求；相邻块重叠部分用 temporal ensembling 平滑。π0 系列用 50 步的块。
  • 异步推理：执行当前块的同时就开始推理下一块，机器人不需要停下来等模型（LeRobot 的 PolicyServer + RobotClient 架构，SmolVLA 论文中提出）。
  • Real-Time Chunking（RTC，Physical Intelligence 2025）：异步时新块和正在执行的块会“接不上”。RTC 把生成新块看作 inpainting：推理延迟期间必定会执行的动作被冻结，其余部分被引导与之衔接，在不重新训练的前提下得到平滑连续的动作。
  • 快慢双系统：把慢的语义理解和快的运动控制解耦，各自按自己的频率运行（Helix、GR00T）。
  • 压缩与编译：INT8 / FP8 / INT4 量化、TensorRT 引擎、更少的 flow 积分步、蒸馏小策略；batch = 1 时 kernel launch 开销占比高，CUDA graph / JAX jit 很关键。
  • 远程推理：机器人只做传感与控制，策略跑在附近的 GPU 上（openpi 用 websocket 提供策略服务）；要处理网络抖动和断连回退。
  • 仿真与世界模型：训练和评测依赖大规模 GPU 仿真（Isaac Sim / Isaac Lab）和视频世界模型（NVIDIA Cosmos 等），它们本身也是推理负载（大批量、扩散生成）。

12Coding Agent 的推理：长会话、高命中、慢工具

代码是目前 LLM 商业化最成功的场景之一，但“写代码”背后其实是三种完全不同的推理负载：编辑器内的行内补全、把建议应用到文件的快速编辑（apply），以及自主完成任务的 agentic coding（Claude Code、Codex、Cursor Agent、OpenHands 等）。它们对 serving 的要求差别之大，几乎可以当成三个产品来设计。

Serving 侧的具体做法

  • 把命中率当一等指标。监控 per-session 的 cached-token 比例；路由用会话 ID 或前缀哈希做粘性，再叠加负载感知（06 的 KV 感知路由）。商业 API 的 prompt caching（例如 Anthropic 默认 5 分钟、可选 1 小时 TTL 的缓存）就是把“工具空档里保留 KV”这件事产品化。
  • KV 的生命周期跨越工具调用。GPU 上用 LRU 保留，压力大时下沉到 CPU / SSD（LMCache、HiCache、Mooncake、Dynamo KVBM）；按 4.2 的估算，载回远比重算便宜。
  • 长上下文 prefill 的成本控制：chunked prefill 防止一个 200k prompt 卡住别人；必要时用上下文并行；agent 侧做上下文压缩、子 agent 拆分任务，减少单会话上下文长度。
  • 可靠的工具调用：每个模型家族的 tool-call 格式不同，引擎里的 tool parser / reasoning parser 必须和模型模板严格匹配；必要时用结构化输出约束参数 JSON。
  • Sandbox 是推理链路的一部分：每个会话一个隔离环境（容器 / microVM），要快速创建、可暂停恢复、可快照；训练（agentic RL）和线上用的是同一套。阿里开源的 OpenSandbox 就是面向 coding agent、GUI agent、评测和 RL 的通用 sandbox 平台（Docker / Kubernetes 运行时，多语言 SDK，内置 MCP server），见 14。
  • 评测：SWE-bench 系列（真实仓库 issue → 补丁 → 在容器里跑测试）、Terminal-Bench 等；评测本身就是“推理 + 大量 sandbox”的负载。

13AI for Science 的推理：结构、几何与物理

科学模型的输入不是自然语言，而是蛋白质序列与多序列比对、原子坐标、基因组、全球气象网格。这些数据的结构决定了模型结构（成对表示、等变网络、图网络、超长卷积），进而让推理负载和 LLM serving 很不一样：batch 往往为 1、显存随问题规模平方增长、CPU 侧预处理可能比 GPU 推理还慢、对数值精度更敏感、大量是离线批量筛选。

模型特征 → 场景 → 推理负载

模型特征为什么这样设计（科学问题决定）在推理负载上的体现
蛋白 / 复合物结构预测（AlphaFold2/3、OpenFold、Boltz、Chai-1、Protenix）：维护 N×N×c 的成对表示，用三角乘法 / 三角注意力更新结构本质是残基两两之间的几何关系，三角更新近似强制“三角不等式”一致性显存随残基数 平方增长，三角注意力计算接近 立方；几千残基的复合物就会爆显存 → 分块（chunking）、低精度、专用三角注意力 kernel；每个复合物单独推理，batch≈1，形状各不相同（难以 CUDA graph）
以 MSA（多序列比对）和模板为输入同源序列的共进化信号揭示哪些残基在空间上接触推理前要在 TB 级序列库上做 jackhmmer / HHblits 搜索，CPU 小时级，常常比 GPU 推理慢得多 → MMseqs2（ColabFold）加速、MSA 缓存与共享服务、GPU 加速搜索
AF3 类模型的扩散结构模块 + 多 seed 采样与置信度排序全原子（蛋白、核酸、小分子、离子）生成，需要多样本评估置信度一次预测 = 主干一次 + 扩散几百步 × 多个样本 → 吞吐与延迟都看扩散部分；可以像 10 一样批量化多个样本
蛋白 / DNA 语言模型（ESM-2/ESM3、Evo 2）：Transformer 或卷积–注意力混合（Evo 2 的 StripedHyena 2），上下文最长到百万碱基基因组有长程调控关系；进化数据量巨大，适合自监督最像 LLM 的科学负载：主要是批量 embedding / 打分（整个蛋白组、变异效应评分）而不是交互生成 → 吞吐优先、离线；长序列需要长卷积 / 上下文并行 kernel
天气 / 气候模型（GraphCast：网格上的 GNN；FourCastNet：频域算子；GenCast：扩散集合预报）全球格点、物理场之间的相互作用；预报本身是概率性的自回归滚动几十步（例如 6 小时一步滚 10 天）；集合预报要几十个成员 → 天然的批；输入输出是 TB 级再分析数据，I/O 与数据管线常是瓶颈；需要在 HPC 定时批量运行
机器学习原子势（MLIP）（MACE、NequIP / Allegro、Meta 的 UMA）：E(3) 等变图网络，球谐与张量积物理量在旋转 / 平移下必须正确变换（能量不变，力等变），保证分子动力学稳定嵌在分子动力学循环里跑百万步，每步一个小图（几百到几千原子）→ 延迟与 kernel launch 主导；等变张量积 kernel 是热点（cuEquivariance）；常要求 FP32 甚至 FP64 精度，BF16 可能破坏能量守恒
科研 agent（文献、实验规划、调用仿真工具）把 LLM 当作科研助理本质上和 12 的 coding agent 一样：长上下文、多轮工具调用、sandbox 执行代码

例题：Llama-3-70B（BF16）放在 8×H100 上，TP=8，能装多少 KV？

高频问题

为什么 decode 是 memory-bound？怎么提高它的硬件利用率？

每个 decode step 每个请求只处理 1 个 token，却要把全部权重从 HBM 读一遍，算术强度约等于批大小 B，远低于 H100 约 295 FLOP/byte 的脊点；attention 读 KV 的强度约为 1，且不能被批摊薄。

  • 加大批：continuous batching + PagedAttention 腾出 KV 空间 + 量化 / MLA 缩小 KV。
  • 减少字节：权重 FP8 / FP4、KV FP8。
  • 一次算多个 token：投机解码、MTP。
  • 减少 CPU 空泡：CUDA graph、重叠调度。
解释 PagedAttention，它的代价是什么？

KV 按固定大小 block 分页，block table 把逻辑块映射到物理块，按需分配，消除预留浪费和外部碎片，并支持引用计数共享与 copy-on-write。代价：attention kernel 需要间接寻址（早期比连续布局慢一些，现在 FlashInfer / FA 已基本抹平）；block 太大有内部碎片，太小则元数据和寻址开销上升；所有 kernel（attention、KV 写入、拷贝）都要支持分页布局。

vLLM 的 prefix caching 和 SGLang 的 RadixAttention 有什么不同？

vLLM 用“父哈希 + 本块 token”的链式哈希给每个满 block 编号，查表 O(1)，只能以 block 为粒度命中；SGLang 用 radix tree 存 token 序列，可以 token 粒度匹配，天然表达树状共享，并配合 cache-aware 调度和 LRU 叶子淘汰。两者效果在常见负载上接近，radix tree 在复杂分支（多轮、树搜索、多采样）上更直观。

Chunked prefill 和 PD 分离，什么时候用哪个？

两者都解决 prefill 干扰 decode。chunked prefill 在同一 GPU 内按时间切分，零额外基础设施，中小规模首选；代价是 prefill 效率略降、两阶段仍共享并行配置。PD 分离在空间上隔离，适合大规模、长 prompt、TTFT 和 TPOT SLO 都严格、或两阶段需要不同并行度（如 DeepSeek 的 EP32 vs EP144）的场景；代价是 KV 传输（需要 RDMA）和系统复杂度。

投机解码为什么能保证输出分布不变？什么时候不该用？

验证时对每个 draft token 以 min(1, p_target/p_draft) 的概率接受，拒绝时从 (p_target − p_draft)₊ 归一化后的分布重新采样，可以证明最终每个位置的分布与目标模型直接采样完全相同（贪心时就是逐 token 比对）。高并发（GPU 已 compute-bound）、接受率低（高温、开放创作）、draft 成本高时收益为负。

MoE 推理的主要挑战？为什么 DeepSeek 用 DP attention + 大 EP？
  • 显存按总参数算，计算按激活参数算；decode 时每个专家分到的 token 很少，GEMM 小而 memory-bound。
  • EP 带来每层两次 all-to-all，且负载不均。
  • 宽 EP 让每卡只放少数专家，显存留给 KV，全局 token 汇聚后每专家批变大；MLA 不适合 TP，所以 attention 用 DP。配套 DeepEP、TBO 重叠、EPLB 冗余专家、DeepGEMM grouped GEMM。
TP、PP、EP 怎么选？

先看能否放下：单卡放得下就用 DP 多副本。放不下时机内优先 TP（降延迟，需要 NVLink）；跨机时 TP 通信太贵，用 PP（不降单 token 延迟）或对 MoE 用 EP。TP 太大时每卡 GEMM 变瘦、通信占比上升，收益递减。长 prompt prefill 可加 CP。MoE 的常见组合是 attention DP（或小 TP）+ 专家 EP。

线上 TTFT p99 突然变差，怎么排查？
  • 拆解 TTFT：排队时间 vs prefill 时间（看引擎的 queue time 指标）。
  • 排队变长：流量上涨、扩容滞后、某实例被路由打爆（看各实例负载是否均衡）、抢占重算增多（KV 不足）。
  • prefill 变长：长 prompt 比例上升、前缀命中率下降（路由策略或会话粘性变化、cache 被挤出）、chunk 设置变化。
  • CPU 侧：tokenizer / 多模态预处理成为瓶颈、API server 进程不够。
  • 最后看硬件：降频、NVLink / 网卡异常、某张卡 ECC 错误。
设计一个支持大量用户的聊天服务（system design 骨架）
  • 需求：模型规模、QPS、ISL/OSL 分布、TTFT / TPOT SLO、成本目标。
  • 容量估算：用 Little 定律算并发 → 算 KV 需求 → 每实例并发上限 → 实例数；用基准曲线选满足 SLO 的批大小和每 GPU 吞吐。
  • 单实例：引擎选型、并行方式、量化、chunked prefill、前缀 cache、投机。
  • 集群：API 网关（鉴权、限流）→ KV 感知路由 → （可选 PD 分离）→ 分层 KV 池；按队列 / SLO 指标自动扩缩；多区域。
  • 可靠性：健康检查、重试、优雅下线、降级（换小模型、限制 max_tokens）。
  • 观测：TTFT / ITL 分位数、命中率、KV 使用率、错误率、成本看板。
量化模型上线前怎么验证？

先确认 kernel 路径（是否真的走了 FP8 / FP4 Tensor Core，还是退回反量化）；精度上在目标任务上做回归（数学、代码、长上下文检索、多语言），不要只看 perplexity；用相同采样参数对比输出分布；压测确认吞吐和延迟收益；灰度上线并监控用户侧指标。

RL rollout 和在线 serving 有什么不同？

目标是 step 时间而不是单请求 SLO；权重每步更新（共置用 CUDA IPC + sleep mode，分离用 NCCL / RDMA 广播）；长尾严重（partial rollout、异步 RL、动态采样）；要求推理 logprob 与训练一致（重算 + 重要性采样修正、MoE 路由回放、确定性 kernel）；agentic 任务需要大量 sandbox 和多轮 KV 复用。

Omni / 语音模型的 serving 和 LLM 有什么不同？

一个模型是多个异构阶段（encoder、Thinker、Talker、codec 解码器），各需不同的批处理和资源；阶段间要传张量；输出是实时流，核心指标变成首包延迟和 RTF，要 chunk 级异步交接；全双工需要持久会话和按节拍推进的调度；多模态预处理和 encoder 可以缓存或单独拆分（EPD）。

扩散模型推理怎么加速？

它是 compute-bound 的固定步数迭代：减步数（蒸馏）收益最大；免训练的特征缓存（TeaCache、FBCache 等）复用相邻步特征；视频长序列用序列并行（Ulysses / Ring / USP）和稀疏 attention；CFG 并行；FP8 / 4-bit 量化；torch.compile / TensorRT；VAE 分块与并行。serving 上用异步任务 API、步级批处理、LoRA 热切换。

机器人策略推理为什么不能直接套 LLM serving？

它是闭环实时控制：batch = 1、看最坏延迟和抖动、多速率（VLM 5–10 Hz、动作 50–200 Hz、底层控制 1 kHz）、多在边缘设备上跑、错过周期有安全后果。核心技术是 action chunking、异步推理 + RTC 平滑拼接、快慢双系统、量化编译与 CUDA graph，以及安全监控和回退。

Coding agent 的推理负载有什么特殊？怎么优化？

模型是长上下文、会调用工具、带 thinking 的大模型（多为 MoE），经过 SWE 类 agentic RL 训练；会话是几十上百轮的“追加式”上下文，每轮只追加工具输出，前缀几乎全部可复用，轮与轮之间要等工具执行几秒到几分钟。所以：前缀命中率是核心指标；KV 要跨工具空档保留（GPU LRU + CPU / SSD 分层）；路由要会话粘性或 KV 感知；长 prompt 用 chunked prefill 隔离；TPOT 决定 agent 完成时间；tool parser 必须可靠；sandbox 的创建与快照恢复在关键路径上。行内补全则相反：小模型、极低延迟、高 QPS、大量取消；apply / 编辑用原文件做投机 draft。

AlphaFold 类模型的推理瓶颈在哪里？和 LLM 有什么不同？

成对表示是 N×N×c，三角注意力接近 O(N³)，显存随残基数平方增长，几千残基就要分块甚至 offload；每个复合物单独推理（batch = 1、形状各异）。MSA 搜索在 CPU 上扫 TB 级数据库，常比 GPU 推理还慢，所以要 MMseqs2 加速和缓存。AF3 还有扩散模块和多 seed 采样。精度上以 BF16 / TF32 为主。优化手段：分块、三角注意力专用 kernel（cuEquivariance 等）、MSA 服务化与缓存、按大小分桶调度。

为什么分子动力学里的 ML 势函数（MLIP）推理更看重延迟而不是吞吐？

MLIP 被嵌在 MD 积分循环里，每个时间步都要算一次能量和力，模拟要跑百万步，而每步只是一个几百到几千原子的小图。总时间 = 步数 × 单步延迟，单步又很小，kernel launch 和小算子开销占主导；等变网络的张量积是计算热点。所以要 CUDA graph、融合的等变 kernel，并保证 FP32 级别的数值稳定性（能量守恒）。

nvidia-smi 显示 GPU 利用率 100%，为什么吞吐还是很低？

nvidia-smi 的 utilization 只表示“采样窗口内有 kernel 在跑的时间比例”，一个只占用几个 SM 的 memory-bound kernel 也会显示 100%。应该看 MFU / MBU、SM 占用率、Tensor Core 活跃度（DCGM 的 profiling 指标或 Nsight），并检查批大小是否太小、是否有 CPU 空泡。

什么是 goodput？为什么比 throughput 更合适？

goodput 只统计满足 SLO（如 TTFT < 1 s 且 TPOT < 50 ms）的请求所贡献的吞吐。只看 throughput 时，把批无限加大就能刷高数字，但大量请求已经违约，对业务没有价值。goodput 把延迟约束纳入优化目标，是 DistServe 等工作用来评估 PD 分离的口径。
